# E6 routing and read-tool decision — 2026-10-22

E6 compared the existing application-first router with a **read-only 4B tool-choice candidate** on the uploaded Sardars corpus. The candidate was screened before tool execution: if it could not reliably request the right tool within a bounded model call, adding another production search/tool loop would only add latency and failure paths. The accepted change is a small deterministic router/catalog-query update. No model-requested tool execution was added to the API, and no sources were reindexed.

## Frozen cases and diagnosis

`backend/app/evaluation/e6_cases.json` contains 11 cases: three missed phrasings, a mixed PostgreSQL/product-page request, company history, unsupported policy, general education, unsafe and irrelevant requests, and two role-visibility controls. The initial read-only service replay passed **6/11**. The SKU price and stock paraphrases and “Point me to basin mixers” fell through to company retrieval; the browse miss took **213.701 seconds** on the local 4B model. The mixed request used page-description words as catalog filters and returned no products. The broad Sardars-history query returned a cited but irrelevant Bongio-history passage. Citation identity checks alone did not catch that relevance error.

The initial history case expected the About Us URL. A source audit found that this broad phrasing did not have a directly answering passage in the retrieved evidence; even a targeted search using the existing “How long has Sardars been in business?” FAQ wording yielded an abstention for the broad question. The acceptance criterion was corrected to a safe abstention **after** the initial report, without changing the question. The original response still fails that corrected criterion. Both report versions are retained locally; this correction is not counted as a newly retrieved source hit.

The configured `qwen3:4b-instruct-2507-q4_K_M` was then offered only three explicit read-tool schemas: `search_company_sources`, `get_product_details`, and `search_products`. The probe **never executed its requested calls**. It requested the expected tool on three of five questions (stock paraphrase, browsing, and company history). The price paraphrase and irrelevant request each ended in a `ModelError` at about **60.2 seconds**; one requested company query was merely `history`, which is too broad to establish evidence relevance. Tool-choice precision among returned calls was 3/3, but needed-tool recall was 3/4 and completed-case correctness was 3/5. This screening rejected a live model-assisted follow-up path on this CPU/model; it does not prove such a path would fail with another model or hardware.

## Accepted behavior

- An identifier plus the measured “set me back” or “any … left” wording now reaches the existing authorized `get_product_details` path. The application still resolves the identifier against role-visible PostgreSQL rows at request time and renders exact SKU, price and stock itself.
- “Point me to” now reaches product discovery. Generic request words such as “point,” “page,” and “description” no longer become catalog constraints. An explicit product-page description request sets the existing `prefer_descriptions` flag, so the bounded catalog search favors ready, visible registered pages before the service fetches and reauthorizes their excerpts.
- The broad Sardars-history wording abstains after exact FAQ matching, rather than presenting a brand-history article as company history. This is conservative: a directly supported broad history answer needs a later source/evidence-selection improvement. The retained exact history FAQ cases still answer with citations.

The final read-only E6 replay passed **11/11** with all measured route, tool-choice, exact-fact, description-citation, abstention and role controls passing. Its live median/p95 was **93.3/819.6 ms** and it made no model calls; these timings describe this small selected set, not a production latency guarantee. SQL and vector fingerprints stayed stable. Local raw reports, which include internal answer/source details, are Git-ignored under `data/e6_*.json`.

## Verification and limits

The retained replays passed **26/26 chat, 21/21 uploaded-source, 7/7 seed and 40/40 full-site** cases; all **24/24** expected full-site source hits remained present. SQL and vector fingerprints remained stable in every suite. The full-site live median/p95 was **20.757/62.277 seconds**, showing that E6's fast selected cases do not remove the wider 4B CPU latency tail. The final backend suite passed **676, four skipped**. The local API image was rebuilt and became healthy; its application Python hash `c4c05cf27637bd3339ebff66e9adf646c9145ec9cccf11042ee0c630fa8174e8` matches all four retained regression reports. Two authenticated requests to the rebuilt service returned the expected product and product-search routes, an anonymous request returned 401, and the short-lived test session and its conversations were removed with the original counts restored. Existing application authentication, role/source rechecks, allowlisted Pydantic tools, safe errors and request deadlines remain the authority boundaries; the tool-choice probe did not receive permission to execute anything. This checkpoint did not compare a fully executed model follow-up loop after the early tool-choice gate failed. Independent human review of a broader cited-claim sample and the 4B CPU latency tail remain quality backlog.
