# E7 bounded web search checkpoint — 29 October 2026

E7 adds external search for explicitly recent, public-looking questions. The current `/chat` and `/ask` flow still authenticates before answer work. For a time-sensitive external question, the local 0.6B model is offered `search_web`; the application runs that one registered read tool if selected, and also runs it when the model skips an eligible search. The application sends the bounded snippets to the model and returns only citations to the actual result URLs. Sardars questions, catalog requests, health and unsafe/action requests do not enter this web path. PostgreSQL remains authoritative for SKU, price and stock; authorized company RAG remains the source for Sardars claims.

## Search backend decision

The local pilot uses a pinned SearXNG container and its JSON `/search` endpoint. [SearXNG's API documentation](https://docs.searxng.org/dev/search_api.html) confirms that JSON must be enabled and that queries are passed to external search services. Thus the search service runs locally, **but queries still leave this machine**. The service is bound to localhost on port 18888; the API uses the internal Compose name. The local secret is generated in ignored `.env`, not committed. SearXNG needed no paid API key, and its result backend can be changed without changing model or business logic. The live service returned JSON results for the public probe; its logs also showed a DuckDuckGo CAPTCHA warning, so coverage varies by upstream engine.

A hosted search API such as [Brave Search API](https://brave.com/search/api/) would remove the local search container and may provide a more consistent independent index, but it needs an account, key and payment details. Brave's [API privacy notice](https://api-dashboard.search.brave.com/app/documentation/general/privacy-policy) says ordinary search-query logs can be retained for up to 90 days. No hosted provider is approved or integrated in this prototype. This is an implementation choice for E7, not a claim that SearXNG keeps queries private from upstream engines.

## Bounds and provenance

One web execution is allowed per answer. The query is the validated user question, never a model-supplied rewrite or previous private context. The adapter rejects common company/private strings, email addresses, URLs, long numbers and control characters before egress. Release questions add the word `official` to improve source ranking. The endpoint is fixed to `searxng` or loopback, JSON responses are capped at 64 KiB, HTTP takes at most six seconds, at most 20 candidates are inspected and three HTTPS public-domain snippets enter the answer prompt. Unsafe result URLs and obvious instruction text are dropped. Errors and empty results produce a checked unavailable answer. Existing authenticated question limits remain in force. These checks reduce accidental leakage; they cannot detect every sensitive phrase a user might type.

Web citations have `origin: web`, a `Web:` title, URL and search observation time; the UI labels them separately. An additive migration stores at most three web-citation snapshots with conversation history. Company source IDs remain separate and are still reauthorized when history is read. There is **no live search-result cache**: each eligible turn searches again, and saved web links are historical snapshots that expire with the existing 30-day conversation retention. Snippets are untrusted data, not instructions, and do not make changing Sardars facts current. The application does not fetch full result pages in E7.

The first live sample exposed a false “PostgreSQL 19 stable” answer from a Beta 4 snippet, followed by a Python answer that cited an irrelevant history page. The final release path rejects prerelease promotion and reduces a version answer to a version present in a cited snippet. When generation is misled by a prerelease and an explicit stable/release-notes listing exists, the application reports the highest version **shown in that listing**, not an unqualified claim about the world's latest version. This narrower wording is deliberate because search snippets can be incomplete or stale.

## Verification and model performance

The final eight-case read-only live replay passed **8/8** declared checks: three external current-release searches, plus greeting, general education, Sardars rating, exact PostgreSQL SKU, and unsafe-request controls. All three web cases produced citations to the captured web results; no web tool ran in the other five. The model requested `search_web` in **3/3 eligible cases** (3/8 total turns); the application executed **3/3** requests successfully. An earlier prompt produced **0/3 model requests** and three application fallbacks, which is why the explicit external tool-choice instruction was added. These rates describe this fixed sample, not real user traffic or an estimated population rate.

The final sample used **11 model calls** over eight turns, 3,384 recorded prompt tokens and 302 output tokens. Across all eight turns the median latency was **14.81 s**, nearest-rank p95 **29.25 s**. The three web turns had median **27.77 s** and p95 **29.25 s**; median SearXNG execution was **1.32 s**, median model tool choice **6.29 s**, and median final generation **20.08 s**. The serial CPU-bound local model, rather than search HTTP, dominates the delay. Source/product fingerprint was unchanged. The report is `data/e7_exit_verified_2026-10-29.json` (ignored local data). Earlier failed and diagnostic reports are retained under `data/e7_*.json` for comparison.

The final cited release statements were reviewed against the captured snippets: Python.org's stable-release listing showed 3.15.2; PostgreSQL.org's release-notes listing showed 18.6; Qdrant's official blog snippet showed 1.20. These statements report what the snippets showed at search time. They do not verify that no newer version exists. The general-education control exposed a weakness of the 0.6B model: its first answer was repetitive and ended mid-sentence. A bounded two-sentence cleanup produced a concise, complete answer in the deployed final recheck, but it was still slow (**25.10 s**). Wider freeform answer quality and independent human source review remain for E8.

The final backend suite, frontend unit tests/build and mocked desktop/mobile browser smoke, migration/readiness, anonymous-access check and Compose validation are recorded in `IMPLEMENTATION_STATUS.md`. No company corpus, vectors, product rows or data volumes were reset or reindexed. No paid LLM or hosted search service was added.

## Gold-rate follow-up — 29 October 2026

The saved conversation `1658608b-edf5-4a9e-aa62-e7214f8f3d69` exposed a routing miss outside the original eight-case replay. “Please search from internet and give me the rates of gold” did not match the `latest/today/current` trigger, so company RAG returned gold-coloured bathroom products and the 0.6B model cited them as if they answered a commodity-rate request. The next “latest news today” turn did match and used web citations. This was a routing and evidence-selection error, not missing gold data in the company corpus.

The correction recognizes explicit public web requests and gold/silver market-rate language. It skips company retrieval and PostgreSQL product lookup for those eligible questions, while the existing private/company, SKU and product boundaries still exclude web search. A vague metal-rate request searches for a labelled Pakistan reference and the returned answer names that assumed market. The application quotes a rate only from a snippet with an explicit amount, currency, unit and purity, and labels the search retrieval time; otherwise it asks for the missing market/purity/unit. The model still chooses the offered bounded web tool and receives the snippets, but application checks render the numerical rate to prevent jewelry or catalog prices from becoming a market quote.

The two reported questions passed **2/2** live checks after the API rebuild: both model-selected `search_web`, both calls succeeded, and both returned web citations. The gold reply cited a Pakistan 24K PKR-per-tola snippet; the news reply cited a matching headline snippet. Four live boundary controls passed **4/4** with no web calls, and source/product fingerprints stayed unchanged. Their measured latencies were 43.43 seconds for gold and 25.26 seconds for news. The full backend suite passed **707**, with four skipped. Read-only reports are stored as ignored local files `data/e7_gold_news_replay_2026-10-29.json` and `data/e7_gold_boundary_replay_2026-10-29.json`.

Search-result snippets are snapshots, not authoritative live market feeds. Some gold snippets disagreed and some lacked a visible publication date. The formatter reports one clearly labelled source quote and retrieval time, not a universal current rate. The news sample cited a headline present in a search snippet, but the snippet itself did not independently establish the headline's publication time. Market-price accuracy, news freshness and broader paraphrases remain E8 human-review items.
